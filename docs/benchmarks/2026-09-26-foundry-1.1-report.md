# Foundry 1.1 performance report

This report closes out P6 of `docs/plans/2026-09-25-foundry-premium-plan.md`. It compares the 1.1 work against the P0 budgets, which were set at baseline × 0.8.

## Hosts

| | Baseline (P0) | 1.1 (this report) |
| --- | --- | --- |
| Machine | Apple M4 Pro, macOS 27.0, AC power | Apple M4, macOS 26.2, AC power |
| Build | Installed 1.0.0 (footprint), staged 1.0.0 + P1 slice (signposts) | Staged `build/Foundry.app` from `./scripts/build-app.sh`, release, Swift 6.1 / macOS 15 SDK |
| Accessibility for the driver | Yes | No (`AXIsProcessTrusted() == false`) |

The 1.1 numbers come from a slower chip (M4, not M4 Pro), so wherever a budget holds here, it should hold on the baseline machine as well. The Swift 6.1 build compiles out Liquid Glass and uses the `NSVisualEffectView` fallback, so the cost of `glassEffect` isn't part of these numbers.

## How each number was measured

- **`panel.show`**: `scripts/drive-signposts.swift 30 --reopen build/Foundry.app` while `log stream --predicate 'subsystem == "app.foundry.prototype"' --level debug` was running. This host doesn't grant Accessibility, so the driver can't post the hotkey. It opens the panel by re-opening the running app, which goes through `applicationShouldHandleReopen` → `ShellController.showPanel()` (the same `resetForOpen` → `PanelController.show()` path the hotkey uses). It closes the panel by activating Finder through LaunchServices, and it exits non-zero if the panel is still on screen after any cycle. The span measures the same thing it measured at baseline: it starts in `PanelController.show()` and ends on the main-queue hop after `orderFront`. All 30 of 30 cycles closed cleanly.
- **Search latency**: `FOUNDRY_BENCH_OUT=… swift test --filter SearchLatencyBenchmarkTests`. This is in-process, uses the default registry and 90 ms keystrokes, and runs as a debug build. The live baseline included the 40 ms keystroke debounce that `ecd99eb` removed. Typing into the panel needs Accessibility, so there is no live search re-measure on this host.
- **Footprint**: `benchmark-launchers.swift --only Foundry --bundle "$PWD/build/Foundry.app" --runs 0 --memory-samples 10`, run right after the 30 open/close cycles with the panel hidden. `--runs 0` is new: it samples memory without posting any key events. `--bundle` is new too: it measures a staged build without installing it. The script's `ensureRunning` now also checks the process table, because `NSRunningApplication` returns nothing inside a `swift` script process and the resulting re-open used to show the panel mid-measurement.
- **Idle wakeups**: the `top -l 2 -s 60 -pid <pid> -stats pid,idlew` delta over 60 s, with the panel hidden and the user idle.

## Changes made during close-out

- **Clipboard poll backs off when the user is idle.** On this host, idle wakeups sat at about 1 per second with the panel hidden. `sample` traced them to the clipboard monitor's 0.7 s `Timer`, which has been there since 1.0.0. The baseline's reading of 0 came from a process that had been up for 51 hours, and App Nap had almost certainly throttled it. macOS has no pasteboard-change notification, so polling can't go away. Instead, the timer now checks `CGEventSource.secondsSinceLastEventType`, which needs no permission. After 60 s without keyboard or mouse input, the next poll moves out to 5 s. Opening the panel captures the pasteboard immediately, so a copy made during the backoff still appears in history. The trade-off: while you're idle, two programmatic copies less than 5 s apart can collapse into one entry. Result: 0.12 wakeups/s.
- The driver and benchmark script fixes described above.

## Missed budget: bundle size

The bundle grew from 14,052 KB to 14,604 KB (+552 KB). Sparkle was the one approved source of growth, and it isn't included, because distribution is out of scope. The growth comes from the P2–P5 scope: the Settings window, onboarding, Quicklinks, Script Commands, Apple Shortcuts, file search, the SQLite clipboard store, and the preview pane. These are all native Swift with no new dependencies. The binary was also built with a different toolchain and SDK (Swift 6.1 / macOS 15) than the baseline. Proposed replacement budget: ≤ 15,000 KB without Sparkle.

## Not re-measured here

- Live `search.immediate` and `search.complete` through real keystrokes need a host that grants Accessibility to the terminal. Run `scripts/drive-signposts.swift 30` (hotkey mode) with the same `log stream`.
- The Liquid Glass (`glassEffect`) render cost needs an Xcode 26 / Swift 6.2 build.

## Live keystroke measurement — 2026-09-29, baseline host (M4 Pro)

This host grants Accessibility, so the deferred live run happened. `swift scripts/drive-signposts.swift 48` posts the real ⌘Space hotkey and real virtual-key keystrokes (the script now polls panel visibility per cycle — blind toggles invert if the panel starts open — and types real key codes because `keyboardSetUnicodeString` events never reached the field). Same `log stream` capture as above.

| Metric | First live run | After apps-provider fix | After PreparedQuery | Budget | Result |
| --- | --- | --- | --- | --- | --- |
| `panel.show` p50 / p95 | 19.0 / 35.0 ms | 8.8 / 22.3 ms | **7.8 / 11.1 ms** | 15.6 / 23.4 ms | Met |
| `search.immediate` p50 / p95 | 45.2 / 97.5 ms | 17.0 / 60.2 ms | **16.1 / 53.5 ms** | 41.5 / 54.8 ms | Met |
| `search.complete` p95 | 102.7 ms | 94.2 ms | **88.0 ms** | 69.4 ms | Missed — see below |
| Warmed footprint p50 | — | 50.3 MB | — | 40.1 MB | Missed on this host (the 31.2 MB above was the M4) |
| Bundle size | — | 16,468 KB | — | ≤ 15,000 KB | Missed; growth is 1.1 feature code, no deps |

The first live run exposed a regression the in-process harness never saw: `NSWorkspace.runningApplications` is a ~20-30 ms WindowServer XPC that the apps provider called **per keystroke**, and the 30 s app-catalog TTL blocked publishes on an ~80 ms rescan. `RunningAppsSnapshot` now caches the running set for 2 s (shared by home's running-dot pass), and `InstalledAppCache` serves stale while a detached task refreshes past-TTL data; a changed root signature still reloads synchronously so newly installed apps surface immediately.

The second fix hoisted query tokenization out of per-candidate matching: `SearchScoring.PreparedQuery` computes the normalized string, tokens, and per-token characters once per keystroke instead of ~370 apps × keywords times plus once per ranker pass. The apps provider's p95 fell from 26 ms to 12.8 ms.

`search.complete` misses its budget but the miss is understood, not opaque: new `search.phase2.collect`/`search.phase2.rank` sub-spans show deferred providers contribute ~0 ms for intent-gated queries and ranking ~5 ms — the residual tail is cooperative-pool and main-queue congestion while a burst of keystrokes is still in flight (the 16 ms coalesce is inside the span by design). `search.immediate` — the user-visible first-publish latency — beats its budget; `search.complete` is the refinement wave that re-publishes after deferred results merge, so this is recorded as an accepted limitation rather than faked.

## Instruments pass — 2026-09-29, Time Profiler (same host, 30 s, 24 show/type/dismiss cycles)

- Main-thread CPU: 3.55 s of the 30 s window (~12%) while the panel was being repeatedly shown, typed into, and dismissed — no single-stack hotspot.
- Inclusive stacks are dominated by `NSPerformVisuallyAtomicChange` (6.7 s inclusive), SwiftUI layout (`LayoutEngineBox.sizeThatFits`, `NSView._layoutSubtreeWithOldSize` ~2.7 s) and AttributeGraph updates (~3.7 s) — normal SwiftUI list-render cost, not a Foundry-specific stall.
- Hang tables empty: zero `potential-hangs` / `hang-risks` rows. Liquid Glass material shows no measurable CPU render penalty in this pass; GPU-side cost would need a Metal System Trace, which was not recorded.
- Trace: `/tmp/foundry-render.trace` (not committed; transient artifact).

## Idle cost — 2026-09-29

Verified at code level and measured live: with the panel hidden, widget/agent polling stops in `panelWillClose`, the agent socket defers to first open/+2s, the snippet event tap exists only when expansion is enabled, and the AX retry is bounded. The clipboard monitor stays on by design (the feature requires it) but backs off to 5s when input is idle.

Live sample on the installed app (pid, panel hidden): `ps -o time` stayed at `0:00.50` across a 30 s window — zero measurable CPU. Lifetime total ~0.5 s CPU in ~85 min uptime.
